# Security assessment and threat model

Assessment date: **2026-10-27**. Scope: the published Nylzo 0.1.1 application, its Go server and CLI, browser client, protocol, storage, Compose deployment, and the reviewed release controls. This is a project self-assessment based on source review, protocol requirements, and automated security tests. It is not an independent audit or penetration test.

Two cryptographic changes shipped after this date and are not yet assessed here: [attachment compression](https://github.com/misaon/nylzo/pull/166) and [protocol version 2](https://github.com/misaon/nylzo/pull/206) with committed envelopes and expiring key shares. Both need the fresh assessment that the next paragraph requires.

On 2026-11-15 the operator's admin area and its first-party visit counting added a trust boundary: passkey sign-in, a signed in-memory session, `admin.db` and a one-hour list of refused client addresses. The actor, interface and threat rows below cover it from source review and the tests they name. Nobody outside the project has reviewed it.

Review this assessment before a release that changes cryptography, capabilities, message lifecycle, external interfaces, storage, trusted proxies, dependencies, or publishing authority. Update the affected threats, controls, tests, and accepted risks in the same PR. A new protocol primitive or trust boundary needs a fresh assessment rather than an assertion that existing tests still pass.

## Assets and security goals

Protect plaintext, link secrets, passphrases, signing capabilities, server peppers, live-message state, release identities, and administrative credentials. The intended confidentiality property covers stored data and ordinary protocol traffic. It does not cover a compromised sender/recipient device, a hostile browser client served by an operator, or an authorized recipient retaining plaintext.

Availability, expiry, and open counts depend on an honest running server and its persistent state. A server operator can refuse service, delete data, serve modified code, or restore an older database. Expiry cannot revoke copies already obtained by a recipient. These limits are part of the [security model](../guides/Security-model.md), not claims that the implementation can detect every hostile operator.

## Actors, actions, and trust boundaries

| Actor or subsystem | Actions and authority | Boundary |
| --- | --- | --- |
| Sender browser or CLI | Creates keys, encrypts content, uploads an envelope, shares the read link, retains cancellation/status capability | Plaintext and private capabilities remain on the client |
| Recipient browser or CLI | Uses the read capability to claim/download, decrypt, acknowledge, or burn | Link possession grants protocol capabilities; a passphrase also restricts reading and burning |
| Anonymous network client | Requests public metadata, creates messages subject to limits, requests challenges, attempts arbitrary API input | All input is untrusted; resource bounds and authorization apply before state changes |
| Server and SQLite/file store | Enforces signatures, leases, expiry, attempt limits, open counts, deletion, and rate limits; stores ciphertext and operational state | Persistent-state transitions must be atomic; server data alone must not contain decryption secrets |
| Operator's admin session | Enrolls a passkey with a one-time link printed on the server host, signs in, reads aggregate counts, server load and the clients refused in the last hour, signs out | A passkey of the instance's origin opens a session for one in-memory Ed25519 key; every request is signed over a single-use challenge; no route reads or changes a message |
| TLS proxy and hosting operator | Terminates TLS, forwards client addresses, serves the instance and web client, controls host data and availability | Trusted to serve the intended browser code and to supply correct forwarding metadata |
| Link holder or malicious recipient | Can retain plaintext, delete a message (one with a passphrase only with the passphrase), exhaust attempts, or share the capability | Possession is authorization; sender identity and non-repudiation are not provided |
| Attacker with a server backup | Inspects SQLite/WAL, blobs, logs, configuration, and potentially the pepper | Ciphertext confidentiality remains; a stolen link enables the documented offline passphrase attack |
| Dependency publisher or compromised registry | Supplies code/tools consumed by builds | Locked versions, integrity verification, restricted build scripts, review, and scanning reduce supply-chain risk |
| Maintainer and release automation | Reviews code or bounded dependency updates, signs tags, publishes artifacts and provenance | Publishing authority is separate from untrusted test execution; signatures identify provenance, not correctness |

## External interfaces

The [protocol API table](../reference/Protocol.md#6-http-api) specifies methods, paths, authorization, and request/response data for create, metadata, claim, blob, ack, burn, cancel, status, instance, and challenge, and for the visit signal (§6.7) and the operator's admin area (§6.8): enrollment, sign-in, overview, live figures and sign-out. Its following sections define envelopes, signatures, leases, errors, transport bounds, and storage rules. [CLI documentation](../guides/CLI.md) defines command-line input, output, exit behavior, and server selection.

The HTTP surface also includes `/healthz`, browser pages including the operator's `/admin`, hashed assets, transparency/client manifests, crawler metadata, and the canonical public URL. These are registered in [routes.go](../../../internal/server/routes.go) and documented in protocol §9 and the [operations guide](../guides/Operations.md). Browser URL fragments carry capabilities and are not sent as HTTP request targets. Instance metadata and transparency information are public; operator declarations are not independently verified.

Filesystem interfaces are the configured data directory, SQLite files (`nylzo.db` with its WAL, and the admin area's `admin.db` with a rollback journal), encrypted blobs, pepper files, and the CLI's explicit input/output files. Environment/CLI configuration and trusted-proxy behavior are described in [operations](../guides/Operations.md) and [self-hosting](../guides/Self-hosting.md). The release interface consists of immutable GitHub assets, signed checksum manifests, provenance attestations, SBOMs, and digest-addressed GHCR images.

## Threats, controls, and remaining risk

| Threat | Existing controls and evidence | Remaining risk |
| --- | --- | --- |
| Plaintext or capabilities leak through creation or a stolen store | Client encryption; shared protocol vectors; `TestAK1CreateCarriesNoSecrets` and `TestStolenServerRevealsNothing` inspect traffic and stored artifacts | Compromised devices, a hostile web client, or possession of the link change the attacker's authority |
| Ciphertext/header modification or request substitution | Authenticated encryption, a server tag over every blob stored since 0.14.0, checked before an open, a download or a passphrase attempt is spent, and signed request transcripts; `TestAK8TamperingFailsIntegrity`, `TestChangedBlobSpendsNoOpenOrDownload`, `TestRequestSignatureBindsEveryField`, `TestSignatureBindsTheRequest` | A link holder can exercise its documented capabilities; no sender identity guarantee |
| Replay after rejection or restart | Replay/state rules; `TestRejectedRequestsCannotBeReplayed` and `TestReplayAfterRestartIsRefused` | Restoring old storage can restore state; do not represent backups as tamper-proof counters |
| Concurrent reads exceed open limits or break lease/deletion state | Transactional lifecycle and lease rules; `TestAK4ConcurrentClaimsHTTP`, `TestFlowCreateMetadataClaimBlobAck`, and lease-expiry tests | A recipient can copy already decrypted data; server availability remains an operator responsibility |
| Guessing passphrases or locking out another reader | Specified KDF, bounded attempt policy, protocol vectors, `TestAK5PassphrasePolicyHTTP` | Weak passphrases remain guessable with a stolen link and server data; a link holder can exhaust attempts |
| A recorded `X-Nylzo-Create` or `X-Nylzo-Verifier` plus the link tested passphrase guesses offline (F11) | Protocol v3 checks the passphrase with OPAQUE (RFC 9807), so no request or response tests a guess without the pepper ([protocol §2.1](../reference/Protocol.md#21-passphrase-check-opaque)); no component may log the protocol headers either (protocol §10), the server logs none and `TestStolenServerRevealsNothing` searches its log for the registration, KE1, KE2, KE3, `P` and every such header as sent; the `nylzo` Caddyfile adapter refuses access logs, request loggers, `tracing`, FastCGI and `insecure_secrets_log`, and the frontend refuses a configuration that skipped it; `TestCaddyfilesLogNoRequestSecrets` checks the public sites of both deployment profiles at debug level over HTTP/2 and HTTP/3, and CI runs it for every Caddyfile change; `nylzo` refuses `GODEBUG=http2debug`, its Caddy also `QLOGDIR` | The running server, or a copy of it with the pepper, together with the link while the blob lives (RFC 9807 §10.11), and an active attacker at the TLS proxy while the message is created |
| Message enumeration, storage faults, or timing differences expose existence | Uniform error policy and isolated timing acceptance tests; `TestAK21UniformNotFoundAndConflict`, `TestStorageFaultKeepsUniformNotFound` | Operational conditions and external network observations need deployment-specific review |
| Creation floods, slow connections, or forged forwarding headers exhaust resources | Body/header/connection limits, source/global caps, proof of work, disk reserve, exact trusted proxies; AK12/AK22 and Compose proxy tests | Distributed attacks and provider outages remain possible; operators must set caps for actual disk capacity |
| Modified browser code, unsafe asset delivery, or redirected CLI traffic exposes secrets | Verified clients (`nylzo web` and `nylzo open`, the CLI) that take no code from the instance, tested against a hostile server; hash-based static CSP and security headers; signed, logged and reproducible releases; CLI HTTPS-origin and redirect checks; client-manifest verification and the hourly monitor | Stock browsers on the website: not fixable on any browser shipped as of 2026-10-31. Revisit when a browser enforces WAICT by default, when WEBCAT leaves alpha or reaches another browser, or when Isolated Web Apps install on unmanaged computers; the browser extension is the next verified client |
| CI input injection or stolen publishing credentials substitutes a release | Quoted/validated inputs, SHA-pinned actions, separate permissions, protected tags/environments, keyless signatures, immutable assets, policy-content checks | An owner-account compromise can change repository settings; a trusted writer remains an administrative risk |
| Someone steals, guesses or reuses an admin enrollment link | The link exists only in the output of `nylzo admin-enroll` on the server host; the token is 192 random bits in the URL fragment, stored only as SHA-256, valid 15 minutes, used up by the one enrollment it allows and replaced by a newer link; at most 8 passkeys; a wrong or used token answers 401 and, once a passkey exists, lists the sender among the refused clients; `TestAK29EnrollmentLinkAddsOnePasskeyOnce` | A link read from the terminal or its scrollback within 15 minutes enrolls the reader's passkey; `nylzo admin-passkeys` shows it and `nylzo admin-reset` removes it |
| A look-alike site phishes the operator's sign-in | Passkeys only, bound to the instance's origin and relying party id, with user verification required; the server checks origin, relying party hash, flags and signature counter with the Go standard library; `TestRegistrationMatchesW3CVectorAndStillNeedsUserVerification`, `TestAssertionMatchesW3CVectorAndStillNeedsUserVerification`, `TestRegistrationRefusesEveryBrokenRule`, `TestAssertionRefusesEveryBrokenRule` | A compromised operator device or authenticator signs in as the operator |
| A stolen, replayed or cross-site admin request acts for the operator | No cookie or stored credential; the session is a non-extractable Ed25519 key in page memory; every request is signed over method, path with query and a single-use challenge; the cross-origin guard covers `/api/`; sessions end after 15 minutes idle, 12 hours, sign-out or restart; `TestAK28AdminAnswersOnlyToASessionAPasskeyOpened` | Script running in the admin page while the session lives can use the key |
| Brute force against enrollment or sign-in | 192-bit tokens; a ceremony challenge works once and for 5 minutes, and a sign-in challenge is held nowhere, so a flood of requests for challenges cannot push the operator's one out; every failure answers 401, is counted as a held event and, once a passkey exists, lists the client for an hour; the token buckets of protocol §8 apply | Guessing 192 bits is out of reach; a distributed attacker can push older entries off the refused list, which holds 256 |
| Forged visit signals inflate or distort the counts | Signals change only counts, answer `200 {}` whatever happens and pass the token buckets; a document is reported only by whoever served the page, and the report route answers only the nylzo frontend (`NYLZO_EDGE_REPORTS`); robots, script clients, `navigator.webdriver`, more than 60 views an hour and more than 64 visitors from one address or one IPv6 /64 count apart from people; message pages are never counted; `TestVisitSignalsForMessagePagesAreDropped` | Anyone can still inflate the counts, so the operator should read them as an estimate |
| Visit counting or the refused list leaks visitor addresses | Visitors are an 8-byte keyed hash under a key redrawn each UTC day, kept in memory; `admin.db` holds counts only, written after their hour has ended, with visitors and countries per UTC day, no WAL and a journal overwritten after every write; refused clients stay in memory for an hour and are never logged or written; nothing is kept while no passkey exists; `TestAK30VisitCountsKeepNoAddress`, `TestAK29EnrollmentLinkAddsOnePasskeyOnce`, `TestCountsReachTheDiskWhenTheirPeriodEnds`, `TestRemovedRowsLeaveNoCopyBehind` | Whoever controls the running process sees the addresses anyway; on a day with one visitor and one message the day's country count points at the sender's country |
| Script injection in the admin page | The same hash-based CSP, Trusted Types and SRI as every page; its `Connection-Allowlist` adds only `https://db-ip.com/`, the attribution link of the country table; WebAuthn is allowed only on `/admin` | An injection would act inside a live session and see what the operator sees |
| A compromised admin session or passkey | No admin route reads, opens or ends a message; the overview and live answers carry aggregates, server load and the refused clients of the last hour | The attacker learns traffic levels and refused address ranges |
| The frontend's visit reports slow down or break pages | Reports wait in a queue of 256 and go through the route's own proxy after the page is served; a full queue drops them, a backend that counts nothing, has no report address or breaks off its answer pauses them for a minute, a panic of the proxy outside a request is caught, and nothing a client sends shapes a report beyond its address and a User-Agent of at most 512 bytes; `TestFrontendSurvivesAReportTheBackendBreaksOff`, `TestAClientCannotStopTheReports`, `TestFrontendReportsCountedPagesWithoutWaitingForTheBackend`, `TestFrontendIsIndependentOfTheBackend` | Dropped reports undercount visits under load |
| A dependency gains a vulnerability or contains malicious code | Locked Go/npm dependencies, checksum verification, restricted install scripts, dependency review, vulnerability scans, and release artifact scans | Scanners cannot prove the absence of unknown vulnerabilities or malicious behavior |

## Assessment result and maintenance

The experimental [Hetzner/Flatcar profile](../guides/Hetzner-Flatcar.md) introduces local infrastructure state, provider tokens, an image factory, OS updates, and a privileged host updater. Tokens stay off the VPS; plans/state are encrypted, image downloads are signature-verified, and application updates require signed release identity and provenance. A failed persistent-state migration stops deployment rather than restoring consumed message state. The cloud provider and administrator remain trusted; there is no hardware-attested boot or protection from a hostile host. External failure monitoring and operator response remain necessary.

The highest-impact accepted limitation is browser-client delivery: TLS and client-side encryption do not protect a browser from the operator who serves its code. The signed CLI is the alternative for users who need to choose independently verified client code. The next priority is preserving lifecycle atomicity and confidentiality under faults; the protocol tests, race runs, timing tests, fuzz smoke tests, and cross-language vectors exercise those guarantees.

Supply-chain controls establish artifact identity and gate known findings. They do not establish an independent cryptographic review. The project has one human maintainer and a documented review exception. It therefore does not meet the Baseline Level 3 requirement for non-author human approval on every primary-branch change. A bot approval does not satisfy that requirement.

Track newly discovered vulnerabilities through the [disclosure policy](../community/Security-policy.md), publish affected/fixed versions and mitigations, and update this assessment when findings change a trust boundary. Use synthetic data and a local instance for testing; no assessment here authorizes testing another operator's infrastructure.
