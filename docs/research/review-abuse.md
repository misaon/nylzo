# Abuse, rate limiting and resource exhaustion: review of Nylzo protocol v1 on Scaleway

Review date 2026-10-21. Inputs: the Czech design document (Protokol v1, Nasazení, OD13, OD21, threat model T1/T6/T9/T13) and research appendices B, C, D. I did not see the conversation that produced the design. Every external fact I rely on is listed in section (e) with its verification status; cost figures are my arithmetic from Scaleway's published prices.

## (a) Verdicts on the owner's claims

Claim 1, guessing protection: true, with two caveats. The 128-bit id and the 256-bit S make guessing a non-issue; the rate limiter plays no part in that, and the document says so correctly. The caveats are two existence oracles for someone who already holds an id (the 409 on create, and a timing difference from the two-table lookup), which reveal that a message exists, never its content. Publishable wording: "Links cannot be guessed. The identifier has 128 random bits and the key 256; at a billion attempts per second for a year the chance of hitting any existing message is below 10^-18, and a hit without the key returns the same 404 as a miss. A passphrase can be tried at most 100 times per message per day, from all addresses combined."

Claim 2, spam and exhaustion: true for the operator's bill, false for availability. The global daily cap bounds storage and database growth; it does not bound compute, database wake-ups, egress or connection slots, and the per-address limits collapse against IPv6 prefix rotation or a residential proxy pool. Publishable wording: "We cap how much the public instance stores and creates per day. When the cap is reached, creating new messages pauses and reading continues. This protects our costs. It does not guarantee availability: without accounts or CAPTCHAs, a determined attacker can fill the daily cap cheaply."

### Brute-force arithmetic (task 1)

With N live and tombstoned messages, one guess hits an id with probability N/2^128; at N = 10^4 that is 2.9 x 10^-35. The document's worst case, 10^9 guesses per second for a year, gives 9 x 10^-19, and Scaleway caps invocations at 5,000 per second per container, so the realistic ceiling is 1.6 x 10^11 guesses per year and 5 x 10^-24. A hit still needs R, a 256-bit HKDF output of a 256-bit secret, which no online attack reaches. Rate limiting is therefore irrelevant to id and R guessing, and the document separates the two roles correctly. The one place where a limit is a security control is the passphrase: the per-id cap of 100 failures per UTC day is what holds, because prefix rotation defeats the per-address backoff. Over a 7-day TTL that is 700 guesses, which is harmless against a 4-word phrase (about 2^51) and still irrelevant against a 6-character password (2^28, 700 of 268 million). The 7-day tombstone leaks only to R holders, by design; F4 and F5 extend that leak to id holders.

### What the global cap buys (task 2)

It bounds storage (cap x 5 MB x 7 days: at 1,000 creations per day that is 35 GB steady state, EUR 0.28 per month) and the size of `messages`, `leases` and `tombstones`. It does not bound compute (F2), database activity (F2, F7), egress (F6), connection slots (F1) or availability for legitimate creators (F3). Degradation is graceful only for readers: once the cap is spent, reads continue and creation returns 503 for the rest of the UTC day. A cheap availability improvement for the second version: the claim response carries a signed one-time "reply credit" (HMAC, 24 h), so a recipient can always answer a message even while the cap is exhausted.

### Alternatives to hashcash (task 3)

Private Access Tokens are HTTP-level (a 401 with `WWW-Authenticate: PrivateToken`), need no script, and fit the no-external-script CSP; Apple ships them from iOS 16 and macOS Ventura with Cloudflare and Fastly as issuers, and the architecture (RFC 9576) keeps the origin from linking redemption to attestation. They can only exempt clients that have them, never be required, and production issuer access was not verified. Turnstile must load `https://challenges.cloudflare.com/turnstile/v0/api.js` from that exact URL, so the rejection on CSP and privacy grounds stands. API keys on the public instance are accounts by another name; keep them for self-hosting and, in v2, as an optional way to raise limits. Creation tokens without accounts reduce to the reply credit above. Scaleway offers no per-client rate limiting on Serverless Containers: the platform cap is 5,000 invocations per second per container, Edge Services can front a container but its WAF is an OWASP-style paranoia-level filter without rate limiting, and the Starter plan plus WAF add-on costs EUR 4.99 before VAT, over budget. No DDoS statement for serverless products was found.

### Counter implementation (task 4)

Use one statement per hit: `INSERT ... ON CONFLICT (key, window_start) DO UPDATE SET count = rate_counters.count + 1, bytes = rate_counters.bytes + $size RETURNING count, bytes`, then compare the returned values; never read-then-write. Two instances overshoot by at most one hit per window, which is fine for a budget limit. Key windows on the database clock (`now()`), as the lease already does. The salt rotation at UTC midnight splits the hour window crossing midnight and doubles that hour's allowance; accept it. The per-(id, ip) passphrase counters must be incremented inside the claim transaction with `RETURNING`. SQLite uses `BEGIN IMMEDIATE`. Hashing prefixes instead of addresses improves privacy (coarser pseudonym) and effectiveness at once.

## (c) Attack, cost, effect, design response

| Attack | Cost to attacker | Effect today | Design response |
|---|---|---|---|
| Guess id or R | 10^9 req/s for a year, far above the 5,000/s platform cap | Nothing (404) | Stops it; entropy, not rate limiting |
| Guess passphrase online | 100 requests per message per day | 700 guesses per 7-day message | Stops it (per-id cap); per-address backoff is bypassable, acknowledged |
| Lock out the real recipient | 100 wrong attempts with R | Message unusable until midnight UTC | Accepted in OD13; sender sees attempts and resends |
| Existence probe by id (F4, F5, F12) | One create slot or 1,000 timed requests | Learns a message exists | Fails on the "indistinguishable" claim; fix is cheap |
| Creation flood, one /64 or proxy pool (F3) | Near zero; a /64 is a home connection | Global cap spent, 503 for all creators | Degrades for creators, reads continue; prefix bucketing raises the cost |
| Storage fill | Bounded by global cap | Tens of GB at most, cents per month | Stops it (budget) |
| Keep-warm and DB wake-up (F2) | One curl loop | Up to EUR 12.75 compute plus up to EUR 100 database per month | Fails; max scale 1, DB vCPU cap, in-memory bucket, billing alert |
| Claim and metadata flood | Rotating addresses, free | DB load, counter rows (F7) | Degrades; in-memory bucket plus prefix hashing |
| Passphrase-attempt flood | Needs R per message | 100 rows and 300 writes per id per day | Stops it (bounded by the per-id cap) |
| Lying Content-Length, slow upload, slowloris (F1) | 160 sockets | Whole instance blocked for the request timeout | Fails without server timeouts; fix is configuration |
| Lease re-download loop (F6) | Symmetric bandwidth | Unmetered egress | Degrades; count and cap per lease |
| Report spam, false reports (F8) | Free | Operator noise, possible deletion of legitimate messages | Fails if reports trigger action; require R and manual review |
| Malware hosting (F11) | One message, one open | Domain reputation | Degrades; small limits plus fast takedown |

## (d) What not to change

Keep the 128-bit client-chosen id and the 256-bit S; keep the uniform 404 for unknown id and wrong R; keep rate limiting framed as a DoS control and the per-id 100-per-day cap as the only passphrase security control; keep counters for creation and passphrase in the database (the in-memory bucket in F2 is an extra layer in front, not a replacement); keep PoW off by default; keep no accounts and no CAPTCHA; keep the global cap returning 503 for creation only; keep Content-Length enforcement and no server-side decompression; keep the 7-day tombstone visible to R holders; keep the sweep as a separate Serverless Job.
